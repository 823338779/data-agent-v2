# Agent Git 仓库维护与确认提交设计

日期：2026-09-16

状态：用户已确认，按最小侵入边界实施

适用范围：Data Agent V2 单实例部署

## 1. 目标与已确认决策

引入独立 Git 仓库服务，作为指标定义的权威存储。Agent 通过本地 `agent-git` 模块提供的文件与 Git Tools 修改仓库，用户通过变更卡片按钮确认后，服务端创建 commit 并推送到远端 `main`。

用户已明确的边界：

1. 首版使用本地 `agent-git` Maven 模块，不引入 MCP。
2. 所有会话共用一个远端仓库，目标分支为 `main`。
3. 每个会话使用独立本地工作区，支持同一需求的多轮编辑。
4. 首版直接提交主分支，不创建任务分支，不引入 PR 流程。
5. 所有拟提交的文件变更必须经过卡片按钮确认。
6. Agent 的责任终点是确认提交已成功推送；不查询、不等待指标平台生效。
7. 文件与 Git Tools 保持通用，指标维护方法由 Skill 和仓库内规范指导。

这里的 `main` 指指标定义远端仓库的分支，与 Data Agent V2 源码仓库当前开发分支无关。

## 2. 非目标

- 不实现指标平台、指标查询编译器、指标同步状态接口。
- 不把 Git hook 回调成功作为 Agent 成功条件。
- 不引入 MCP、动态仓库管理界面、多仓库选择、分支选择或 PR。
- 不新增认证、租户隔离或 RBAC；继续使用固定身份与租户上下文。
- 不提供模型可调用的任意 Shell、任意 Git 命令或直接 commit/push Tool。
- 不自动合并、rebase、强制推送、改写远端历史或执行仓库内脚本。
- 不提供二进制编辑、子模块、符号链接、Git LFS 或仓库自动初始化能力。
- 不引入分布式任务队列、跨节点工作区或通用审批流程引擎。

## 3. 总体架构

```text
用户请求
  -> ReAct Agent
  -> skill_read：git-repository-maintenance
  -> agent-git 文件与工作区 Tools
  -> 当前会话的本地 clone
  -> 冻结候选快照并发布 git-change-card

用户点击卡片“确认提交”
  -> agent-web 确认接口
  -> agent-git 提交服务
  -> 检查基线、创建 commit、push main
  -> 更新卡片为已推送并返回 commit ID

独立 Git 仓库服务
  -> 可由运维另行配置 post-receive
  -> 指标平台自行接收和刷新（Agent 不参与）
```

Git CLI 是本地执行手段。服务端使用固定可执行文件和参数列表调用，不经过 Shell 拼接；凭据、远端地址和工作目录不能由模型指定。仓库来源不赋予执行权限，读取仓库中的说明也不能改变服务端的工具边界。

## 4. Git 组件及配置

首版对接已配置的 Git 服务端仓库。Git 服务可作为独立进程或容器部署，持久卷保存裸仓库；首次由部署人员初始化 `main` 和仓库说明，Agent 不隐式创建远端仓库。

Agent 配置包含：启用开关、固定仓库标识、远端地址、Git 可执行文件、本地持久工作区根目录、提交作者和凭据引用。目标分支固定为 `main`。仓库凭据通过部署环境配置，不能写入定义文件、模型输入、卡片或日志。

部署约定：远端 `main` 禁止删除和非快进更新。Git hook 配置由运维管理，不由 Agent 编辑。首版交付 Git 组件部署及接入说明，不构建独立的 Git 管理控制面。

启用时检查本机 Git、持久目录和配置完整性；远端暂时不可达表现为工作区准备或推送失败，不阻止非 Git 对话继续运行。关闭能力时不开放相关 Tool，也不创建工作区。

## 5. 工作区与文件操作

### 5.1 生命周期

每个会话按需创建一个独立 clone，所有 clone 的 origin 相同。使用服务端生成的工作区标识定位目录，不接受模型提供绝对路径。每个会话最多有一份可编辑草稿；工作区绑定会话，不能通过猜测其他工作区标识跨会话操作。

第一次准备时 fetch `main`，将远端提交记录为 `baseCommit`。工作区没有草稿且未在提交时，可以刷新到最新 `main`；有未提交变更时重复准备只返回当前状态，不执行 pull/reset。

首版保留工作区与已登记快照，不做后台自动清理。服务重启后校验本地文件与记录完整性再使用；文件缺失或摘要不匹配时标记不可继续，不能静默重建并保留旧确认。

### 5.2 并发

同一工作区的读取快照、文件修改、卡片冻结和提交使用互斥控制，文件修改还检查调用方读取的文件摘要。不同会话可以并行编辑。

首版同一仓库的提交任务串行执行，等待期间不得占用数据库长事务。确认接口只登记任务，后台执行前重新检查远端基线。远端仍可能存在其他写入者，因此正常 push 的非快进拒绝是最后的竞争保护。

### 5.3 文件范围

只处理工作区内受支持的 UTF-8 普通文本文件。拒绝路径穿越、绝对路径、`.git`、符号链接、子模块、二进制和超限文件。服务端同时验证目标路径及父目录，不只做字符串前缀判断。

新增、修改、删除使用带预期摘要的结构化文件操作：新增要求原路径不存在；修改和删除要求原文件摘要一致。Tool 生成的新文件不得因 gitignore 而在确认时静默遗漏；不支持的文件或路径在编辑时直接报错。

初始上限：单文件 512 KiB；一次文件操作最多 20 个文件；一份候选变更最多 100 个文件、5 MiB 新旧内容总量和 2 MiB 完整 diff。上限由服务端配置，模型不能提升。超过卡片范围时拒绝创建候选，不生成只展示部分内容却允许提交全部文件的卡片。

## 6. Skill 与 Tools

新增 bundled Skill `git-repository-maintenance`，读取后按现有机制激活下列 Tool：

| Tool | 输入重点 | 行为 |
| --- | --- | --- |
| `git_workspace_prepare` | 无仓库或路径参数 | 准备当前会话工作区，返回基线和草稿状态 |
| `git_files_list` | 相对目录、分页参数 | 有界列出文件 |
| `git_files_search` | 搜索词、相对目录 | 有界搜索文本，返回路径与位置 |
| `git_file_read` | 相对路径、行范围 | 返回文本和完整文件摘要 |
| `git_files_apply` | 文件操作、预期摘要 | 修改当前工作区，增加草稿修订号 |
| `git_diff` | 无 Git 命令参数 | 返回当前变更摘要与有界 diff |
| `git_change_prepare` | 业务摘要、提交说明、预期草稿修订号 | 冻结候选并生成确认卡片 |

Tool 的会话归属通过现有服务端 execution 上下文解析；不信任模型提供的 sessionId。必要时由 `agent-web` 在 execution 启动时注册工作区会话绑定，避免 `agent-git` 依赖 `agent-web`。

Skill 指导 Agent 阅读仓库规范、寻找相关定义、尽量保持修改范围最小、复核 diff，并在创建卡片后说明等待用户确认。首版没有格式专属的指标校验器，检查结果只表达文件与 Git 变更完整性，不声称指标业务口径已由程序验证。

没有提交 Tool。即使模型输出“用户已确认”或参数 `confirmed=true`，也不能产生确认记录或触发 commit/push。

## 7. 候选快照与确认卡片

### 7.1 快照内容

每次 `git_change_prepare` 在工作区互斥保护下：

1. 检查预期修订号和实际草稿一致，拒绝空变更。
2. 收集全部新增、修改、删除，生成候选完整文件树。
3. 保存不可变快照、完整 diff、文件摘要及提交说明。
4. 计算候选摘要，绑定仓库、分支、`baseCommit`、候选内容和提交说明。
5. 持久化候选记录，关联当前 assistant 消息的 `git-change-card@1`。

允许在确认前写入本地 Git blob/tree 对象用于快照；确认前不创建 commit、不移动分支引用、不 push。

新快照先在临时位置写完整后再原子登记；未登记的临时对象不可提交。卡片与候选必须在同一短事务中关联，重复执行相同准备请求返回已创建结果。

### 7.2 卡片内容

- 业务变更摘要和固定目标分支。
- 基线提交、文件变更列表、可完整查看的 diff。
- 基础检查结果及其检查范围。
- 确认提交、取消按钮。
- 提交阶段、错误摘要、成功后的 commit ID。

复用消息 `uiBlocks` 的受控 type/schemaVersion 注册机制，payload 保存 `changeId`，不把全量 diff 放入会话 SSE。卡片挂载时获取详情，diff 按文件加载。提交中采用短时轮询详情接口；终态停止轮询，切换页面或刷新后可以重新获取。Agent 不需要保持运行或重新调用模型来完成按钮操作。

现有 UI Block 投影和查询职责保留在原位置，不做包迁移或职责抽取。复用已有消息查询对不同类型 UI Block 的透传能力，新增 `git-change-card@1` 注册和独立详情接口。`agent-git` 不依赖 Office 产物模块。保留既有 `artifact-card@1` 契约与显示行为。

### 7.3 修改与取消

已生成卡片后，任何实际文件变化都会使该卡片 `INVALIDATED`。生成新卡片同样使旧候选失效。取消卡片只取消提交授权入口，保留可编辑草稿。

`SUBMITTING` 或 `VERIFYING` 期间工作区禁止编辑、生成新候选和取消提交。确认按钮只作用于一份已展示的冻结快照，不批准未来编辑。

## 8. 提交与推送

确认请求只携带 `changeId` 和卡片版本；内容、目标分支、提交说明都由服务端从候选读取。服务端检查会话归属、状态、版本和快照完整性，通过 CAS 将 `PENDING_CONFIRMATION` 转为 `SUBMITTING`，记录确认身份与时间。重复确认同一有效请求返回同一任务，不排入多个提交。

后台任务执行顺序：

1. 取得仓库提交互斥和工作区互斥，读取已确认候选。
2. fetch 固定远端 `main`。若远端不存在或远端提交不等于 `baseCommit`，进入 `RECONFIRM_REQUIRED`。
3. 使用冻结 tree、基线 parent、已冻结提交说明、服务端作者和持久化的提交时间生成唯一 commit 对象。
4. 在 push 前持久化 `commitId`，确保恢复时不会创建内容相同但 ID 不同的提交。
5. 正常推送该 commit 到 `refs/heads/main`，不使用强推参数。
6. Git 确认更新成功后标记 `PUSHED`，工作区基线更新为已推送 commit。

Git 调用期间不持有数据库事务。生成 commit 后、登记前退出时，可以根据固定 tree/parent/message/author/time 重建相同 ID；数据库确认记录是允许继续执行的依据。实现必须禁用会改变 commit 或文件内容的本地 hook、签名和非预期过滤配置，并确保文件换行不会因运行系统变化而静默改变。

确认后 `main` 发生竞争更新，push 的非快进拒绝进入 `RECONFIRM_REQUIRED`。即使文件无冲突，也不自动重写已确认候选。保留旧候选供查看；下一轮维护明确更新基线，Agent 将修改重新应用到最新内容并创建新卡片。为实现该恢复路径，`git_workspace_prepare` 可以提供显式“重新开始草稿”操作，但必须由服务端先归档旧草稿并失效旧卡片；默认 prepare 永不丢弃草稿。

## 9. 状态与恢复

| 状态 | 含义 | 后续动作 |
| --- | --- | --- |
| `PENDING_CONFIRMATION` | 候选完整，尚未确认 | 确认、取消或继续编辑使其失效 |
| `SUBMITTING` | 已确认，正在检查基线、commit 或 push | 等待 Git 结果 |
| `VERIFYING` | push 可能成功，结果尚未核实 | 只核实远端 Git |
| `PUSHED` | 目标 commit 已被远端 main 接受 | 完成，不联系指标平台 |
| `RECONFIRM_REQUIRED` | 基线变化，不能使用原确认继续 | 更新草稿并创建新卡片 |
| `INVALIDATED` | 内容修订或新候选替代 | 原卡片不可确认 |
| `CANCELLED` | 用户取消候选 | 保留草稿，可创建新卡片 |
| `FAILED` | 已知提交未完成或本地快照损坏 | 展示原因，由用户重试或重建草稿 |

push 超时、连接中断或进程在 push 附近退出时，先进入 `VERIFYING`。fetch 后检查 `commitId` 是否等于远端 main 或是其祖先；已包含即标记 `PUSHED`，即使分支已有后续提交也不再次推送。

如果 Git 可达且确认不包含该 commit：基线仍一致时保留原 commit，提供用户“重试提交”入口；基线已变化时要求重新确认。远端不可达时保持 `VERIFYING`，展示“结果待核实”，由页面的核实按钮或启动恢复任务重新核实，首版不进行无限后台重试。

服务启动时核实遗留的 `SUBMITTING`、`VERIFYING` 记录。确认记录存在但没有 commit 时，不自动继续写入，标记可重试失败，由用户触发；未确认候选始终不自动提交。恢复只处理 Git 变更记录，不恢复原 ReAct execution。

重试提交仍绑定原候选和已记录的 commit；只在快照完整、草稿未变化且基线仍适用时执行。重复重试同样使用 CAS 去重。

## 10. 最小持久化模型

### `git_workspace`

- 工作区 ID、会话 ID、固定仓库标识。
- 服务端存储键、基线 commit、草稿修订号。
- 活动候选 ID、工作区状态、版本号和通用审计字段。
- 同一会话与仓库最多一个工作区。

### `git_change`

- 变更 ID、工作区 ID、会话 ID、消息 ID。
- 分支、基线 commit、tree ID、快照存储键、候选摘要。
- 业务摘要、提交说明、草稿修订号、文件统计。
- 状态、确认时间与身份、固定提交元信息、commit ID。
- Tool 准备请求幂等键、错误码与脱敏摘要、版本号和通用审计字段。

数据库保存元数据，受控持久目录保存候选文件和完整 diff。SQL、凭据、Git 原始 stderr 不进入日志；文件内容和 diff 仅通过归属校验后的接口提供。目录路径不对模型或用户暴露。

持久化实现统一放在 `agent-persistence`，优先使用已有基类、MyBatis-Plus CRUD、类型安全 Wrapper 和版本控制能力。数据库迁移为表和字段写中文注释；不提前固定迁移序号，实施时接续仓库最新序号。

## 11. HTTP 契约

以下接口统一位于 `/api/v1/agent-sessions/{sessionId}/git-changes`：

| 方法与后缀 | 用途 |
| --- | --- |
| `GET /{changeId}` | 卡片详情与最新状态 |
| `GET /{changeId}/files` | 候选文件列表 |
| `GET /{changeId}/diff?fileId=...` | 获取服务端登记文件的完整 diff |
| `POST /{changeId}/confirm` | 确认并登记异步提交 |
| `POST /{changeId}/cancel` | 取消未提交候选 |
| `POST /{changeId}/retry` | 用户重试已知失败的同一提交 |
| `POST /{changeId}/reconcile` | 核实不确定的 push 结果 |

确认、取消、重试请求带预期记录版本。有效重复请求返回当前任务；不匹配的版本或失效候选返回稳定冲突码。首次确认成功登记后返回 202；状态查询不访问指标平台。接口不接受任意文件系统路径或远端 URL。

## 12. 模块职责

| 模块 | 本次职责 |
| --- | --- |
| `agent-git`（新增） | Git CLI、工作区、文件操作、候选快照、Tools、提交与 Git 核实 |
| `agent-skill` | bundled 仓库维护 Skill 与工具依赖声明 |
| `agent-domain` | 必要的变更状态和值对象 |
| `agent-persistence` | Entity、ServiceImpl、迁移、状态 CAS 与元数据查询 |
| `agent-web` | 会话绑定、确认 REST、Git 消息卡片发布；复用已有 UI 投影 |
| `agent-server` | 运行时配置与装配 |
| 前端 | `git-change-card@1`、diff 查看与按钮操作 |

`agent-git` 依赖 `agent-tool`、`agent-domain`、`agent-persistence`，不依赖 `agent-web`、`agent-skill` 或 `agent-artifact`。`agent-skill` 可依赖 `agent-git` 的公开 Tool 标识，保持依赖单向。模型可见 Tool 的注册仍使用现有统一供给机制，不复制另一套 ReAct 循环。

`git_change_prepare` 通过 `agent-git` 定义的窄接口请求卡片发布，`agent-web` 实现该接口并完成消息归属检查、候选登记与 UI Block 关联的短事务。文件快照在事务前生成；提交失败留下的未登记快照不可进入确认流程。这样 Tools 无需反向引用 Web 模块，候选与卡片也不会出现一方成功、一方缺失的已登记状态。

沿用项目构造器注入、Lombok、record、MapStruct 和语义化组装工厂约定。新增持久化操作不手写已有框架提供的通用 CRUD。

侵入边界：不重构 ReAct 循环、`AgentTool` SPI、会话执行状态机、上下文压缩或数据分析 Workflow。Git 确认发生在独立 HTTP 接口，不使原 execution 暂停、等待或恢复。只扩展模块依赖、注册、配置、卡片契约和必要业务接口。

## 13. 验证与完成条件

### 模块测试

- 使用临时本地裸仓库和真实 Git CLI，验证 clone、文本增改删、diff 和 push。
- 两个会话草稿互不影响；同一会话文件摘要过期时拒绝覆盖。
- 未确认时无法 commit/push；候选摘要或快照被改动时拒绝提交。
- 修改草稿、替代候选、取消后，旧卡片不能继续确认。
- 重复确认和重试只生成一个 commit，提交 tree 与确认快照逐字节一致。
- 两个会话竞争 main 时，一个成功后另一个要求重新确认。
- 模拟 push 成功但响应丢失，能够通过远端历史判定成功。
- 模拟进程中断、远端暂时不可达和快照缺失，状态不误报成功。
- 路径穿越、符号链接、二进制、超限内容及任意命令参数被拒绝。

### 接口与前端测试

- 卡片绑定真实候选，确认按钮调用服务端接口，不依赖模型宣称确认。
- 完整 diff 可查看；失效、提交中和已推送卡片按钮正确。

### 首版完成标准

用户在任意会话提出文本定义修改，Agent 能在独立工作区完成编辑并生成确认卡片；用户确认后，已审阅的内容恰好形成一个 commit 推送至共享远端 main；重复请求、并发提交和不确定网络结果不会造成未确认内容发布、他人提交覆盖或虚假成功。Agent 以“已推送”结束，不等待任何下游状态。

### Task 3 实施补充：终答保持卡片可见

正常模型终答会替换 assistant 正文，因此在 `ModelInvocationCoordinator.completeFinalAnswer` 原终答落库点增加一次可选 Git 组装调用：根据当前消息已登记的 `git-change-card@1` 补回占位符，并将同一正文写入最终流检查点。该变更是卡片在 execution 结束后仍可见、可确认的必要接入，不重构 ReAct 循环、Tool SPI 或状态机；artifact 投影与行为保持原样。关闭 Git 时不装配组装服务。

卡片 payload 明确为 `{changeId, sessionId}`，两个 ID 均由服务端从候选和可信执行关联生成。部署配置、资源限制和精确 HTTP 契约见 `docs/agent-git-runtime.md`。
