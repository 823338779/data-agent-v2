# ReAct 步骤级上下文压缩设计

日期：2026-10-04。状态：书面规格已获用户确认；实施计划待评审，尚未进入实施。

## 1. 目标与已确认边界

用户只发送一条请求，Agent 在同一 execution 中连续进行大量 ReAct 交互时，可以多次压缩已完成的过程，并继续完成原任务。跨用户轮次与用户轮次内部使用同一套滚动摘要规则。

成功标准是：压缩后目标、约束、事实来源和业务对象身份可恢复；工具调用与结果始终配对；已执行的写操作不会因为压缩而重复；不要求用户新建会话来规避正常的历史增长。

用户已认可：按 token 预算触发、以完整 ReAct 步骤组为单位、近期原文保留受预算约束、大结果有界呈现并可按需读取、摘要记录轮内覆盖位置。

实现归属为 `data-agent-v2`。沿用单会话最多一个 running execution、运行期间禁止追加 user 消息、现有取消与执行权检查。Metric Platform、dbt-service、dbt/MetricFlow vendor 不承担上下文压缩职责。LSM/raw 的历史选择与摘要协议不在本次调整范围。

本规格取代 `2026-08-25-session-wide-hierarchical-context-design.md` 中“最近十轮固定保护”和整轮摘要资格的约束。全会话读取、只由真实 user 消息定义用户轮次、失败空 assistant 不得遮蔽后续请求等既有规则继续有效；步骤是否可压缩与用户轮次身份是两个不同问题。

## 2. 当前代码与问题证据

| 当前实现 | 约束与本次变化点 |
|---|---|
| `ReactExecutionEngine` | 每次模型调用前已经执行 `contexts.prepare`；工具组执行完成后进入下一轮，保留这个同步检查点 |
| `HierarchicalConversationHistoryLoader` | 从会话全部消息和 thinking process 重建历史；继续读取真实持久化来源，增加步骤级投影 |
| `ConversationTurnGrouper` | 按 user 消息分组，整轮不可拆分；保留用户轮次语义，但不再把它当压缩最小单位 |
| `HierarchicalContextPolicySnapshot` | 硬编码保护最近 10 个用户轮次；改为预算内选择原文后缀 |
| `HierarchicalConversationContextAssembler.historyMemoryBudget` | 保护后缀已超预算时，在摘要调用之前退出；改为先确定最小必要输入，再规划历史压缩 |
| `RollingColdCompactionPlanner` / `RollingColdSummaryGenerator` | 按完整轮次分批；一个超大轮次也无法送入摘要模型，需改为完整步骤组分批 |
| `EventSummaryCoverage` 与共享 V2 摘要校验 | 只有轮次与消息范围，无法区分同一 assistant 消息中的多个模型调用；新增 Hierarchical 专属 V3 覆盖协议，V2 继续服务旧摘要和 LSM |
| `ConversationProcessCoordinator.finishTool` | JSONB 只保存有界载荷，完整安全输出另写审计日志；日志不是可查询的持久化结果库，不能假设已有原文读取能力 |

端到端测试中，同一会话第三次用户请求内，dbt 校验成功后出现 `HierarchicalContextWindowExceededException`。栈经过 `compactIfRequired → compactionInput → historyMemoryBudget → failProtected`，表明压缩已被触发，但摘要生成尚未开始。只有三个用户轮次时，最近十轮规则把全部工具历史都纳入保护范围。

当前 estimator 以 UTF-8 字节数及协议开销作保守估算，并非 provider 实测 token。本次先保持该口径一致，不通过放宽估算掩盖压缩边界问题，也不新增 tokenizer 依赖。

## 3. 方案选择

采用统一的步骤级滚动摘要，继续复用现有 Hierarchical coordinator、模型端口、不可变 Cold、checkpoint CAS 和执行权检查。

不采用仅减少用户轮数的方案：单轮仍可能过大。不另建独立的“本轮摘要层”：那会额外引入两套摘要的覆盖交接、重复注入与轮次结束合并规则。本设计仅细化一套摘要的覆盖单位。

## 4. 稳定的步骤与覆盖位置

### 4.1 步骤组

一次模型调用发出的全部 `tool_calls` 与对应的全部终态 observations 构成一个原子步骤组。单次发出多个工具时，不以单个工具完成作为边界。工具失败结果也是事实；PREPARED/RUNNING 节点不是可压缩的完成结果。

无工具的模型输出在持久化完成后构成一个完成步骤。运行中的流式片段不可进入已覆盖前缀。最终回答和消息封口必须分别可定位，不能因 assistant 正文为空而把旧失败轮次永久视作当前轮次。

用户消息也是有稳定身份的历史单元。用户轮次用于展示、意图关联与追溯，不限制压缩资格。

### 4.2 游标

新增 Hierarchical 步骤游标，由以下字段组成：

| 字段 | 含义 |
|---|---|
| `messageSequence` | 会话内持久化源消息序号，排序第一关键字 |
| `positionKind` | `MESSAGE_START`、`INVOCATION_END`、`MESSAGE_END`，按此顺序排序 |
| `modelInvocationSequence` | 仅 `INVOCATION_END` 使用的消息内模型调用序号，其余位置固定为 0 |

同一消息内先按位置种类排序，再按模型调用序号排序；不同消息先按消息序号排序。所有游标绑定 `conversationSessionId`，不能跨会话比较或引用。`executionId`、`processItemId` 和源内容摘要作为来源校验信息，不使用随机 ID 排序。

只有已封口的消息才能生成 `MESSAGE_END`。运行中 assistant 消息允许新增更大的 `INVOCATION_END`，旧覆盖位置不因追加而变化。空的已终止 assistant 消息也有封口位置。当前待调用的空模型边界不构成已完成步骤。

覆盖采用 `(fromExclusive, throughInclusive]`。滚动 Cold 表示截至 `coveredThrough` 的连续已发布前缀，后续只追加该位置之后的新步骤；`evaluatedThrough` 单独记录本次观察位置，不能用它丢弃尚未压缩的原文。

当前 user 原请求始终作为独立锚点注入，即使它的历史单元已被摘要覆盖。组装时剔除原文后缀中相同消息 ID 的重复锚点；摘要可以陈述目标，但不能替代原请求或提高其指令优先级。

### 4.3 快照冻结

一次 prepare 冻结已完成步骤前缀、源消息版本、执行身份和内容摘要。摘要期间执行取消、失去执行权或源材料发生不兼容修改，则不得发布该候选。

追加的新步骤留到下一次 prepare，不允许按全量 assistant JSON 的变化误判整个旧前缀失效；核对的是被摘要覆盖的步骤内容。不得更改现有全会话读取语义，重新引入旧的消息上界问题。

## 5. 预算与组装策略

设模型窗口为 W、输出预留为 O、安全余量为 S，可用输入硬预算为 H = W − O − S。估算必须包含系统提示、工具 schema、必要运行时贡献、摘要包装、当前请求和历史，而不是只计算聊天正文。

默认软触发为 `floor(0.70 × H)`，目标为 `floor(0.55 × H)`。两个比例可配置，要求 `0 < target < trigger < 1`；其分母语义与旧配置不同，必须使用新版策略配置并在 README 明确迁移方式，不能静默重解释旧配置。

模型输入按既有角色和信任边界组装：

1. 系统规则、当前工具定义、必须保留的 Skill 约束与必要运行时元数据。
2. 标识为不可信历史资料的滚动摘要。
3. 当前用户请求原文。
4. 最近的完整原文步骤后缀，以及任何尚未完成而不能压缩的协议材料。

原文后缀优先保留最新两个完整步骤组，但这是软偏好；预算不足时可以缩减到一个或零个。不存在“最近十轮即使超限也必须全部保留”的规则。尚未完成的工具配对不得因预算不足被截掉。

运行时可选记忆仍按现有规则在软水位省略；最终输入与估算必须使用同一份贡献选择，不能缩小历史后又自动填满可选记忆。

最小必要输入 P 包括可信规则、当前请求和不可移除的协议部分。只有 P 本身无法装入 H 时才直接报告必要输入超限；可压缩历史过大不得成为进入摘要前的失败条件。

当 P 小于 H 但超过目标水位时，使用剩余硬预算形成有界摘要，并记录无法达到目标水位的原因。发布前再次校验完整输入不超过 H。压缩还必须带来可度量的净缩减；没有缩减时不得循环调用摘要模型。

## 6. 压缩算法与触发时机

在每次下一次业务模型调用前执行：

1. 核实 execution 仍可运行，读取当前工具集合并冻结历史步骤。
2. 从服务端构建固定约束、当前请求及工具结果的有界投影，选择运行时贡献。
3. 估算完整输入；未达到软水位直接使用当前视图。
4. 达到软水位时，从旧到新选择连续的已完成步骤前缀，直到给摘要和原文后缀留出目标预算。
5. 以“已发布摘要 + 新的完整步骤组”分批生成滚动候选。每批输入同时计算摘要提示、schema、旧摘要和本批材料；不是只对原始步骤计数。
6. 校验结构、来源游标、关键事实引用、输出预算与完整输入预算，然后原子发布新 Cold 和 checkpoint。
7. 使用新摘要与未覆盖后缀调用业务模型。原始工具记录不因摘要发布而删除或改写。

一个步骤组过大时先使用第 8 节的有界投影；不能拆开工具调用与结果配对。旧摘要本身过大时可在相同覆盖范围内重写为更短版本，但不得捏造新覆盖位置。

每次 prepare 最多做一次范围规划；生成器可以按有界批次顺序合并。复用现有至多两次格式生成尝试，并受总 execution deadline 限制。达到相同历史与输入指纹的重复失败状态后，不做无限重试。

## 7. 摘要内容与业务正确性

Hierarchical V3 摘要包含事件、当前目标和约束、已验证结果、待完成事项、错误与恢复状态、证据引用。覆盖位置及来源范围由服务端冻结，模型只能在给定范围内生成内容。

关键 ID、版本、写操作是否完成、是否仍需用户确认，由服务端从真实过程及已有业务记录构建结构化执行事实，不能仅依靠自然语言摘要。摘要与这些事实冲突时拒绝候选；引用范围正确不代表事实已经被验证。

指标开发场景至少保留当前 execution 固定的项目、分支、工作区和已观察的修订号，以及相关 validation/change/query 身份与最后观察状态。状态可能在其他会话推进；后续写操作仍由原业务服务检查当前版本、权限、幂等键和确认状态。

摘要不会获得新的写权限，不会触发工具执行，不会把“计划 push”“用户请求修改”“已生成候选”解释为“已确认 push”。压缩也不得减少 ReAct 调用计数、重置执行截止时间或改变当前工作区。

Skill 正文中的执行约束不能交给摘要模型自由删减。按当前 execution 已读取的 Skill 路径和 digest，从冻结资源重建所需指令并去重；摘要仅记录读取事实和相关业务结果。保留现有来源标识和指令层级，不把普通工具输出升级为 system 指令。必要指令过大时明确报必要输入预算不足。

## 8. 大结果保存、读取与轮询

### 8.1 持久化安全原文

复用 `ProcessPayloadSanitizer` 的脱敏输出和现有 `BoundedProcessPayload` 预览。对于需要从模型输入移出的工具参数或结果，新增由 `agent-persistence` 承载的安全载荷记录，保存会话、execution、process item、输入/输出方向、内容摘要、字节数、正文和来源类型。

记录使用稳定业务 ID；同一来源和内容摘要重复写入应收敛。工具终态发布前保证引用已经持久化，不能向模型发放未落库的引用。工具已经产生外部副作用而保存失败时沿用已有失败/核实路径，不自动重跑工具来补数据。

安全载荷与所属会话过程采用相同的保留周期和可见性；不能因为载荷被摘要引用就永久保留，也不能在活动会话仍依赖它时单独清理。会话不可见时读取入口同步不可见。本次不增加独立的后台 GC 系统。

默认单份原文持久化上限为 1 MiB，可配置且有正数校验。超过上限必须显式标注原文未完整保存，并保留工具原生资源读取入口（如文件、查询、验证产物）；不得伪造“全文可恢复”引用。旧记录只有截断预览时，同样如实标明，不能扫描日志冒充事实库。

### 8.2 有界模型投影与读取工具

大载荷在模型输入中表示为状态、重要身份字段、摘要/预览、原文引用、摘要校验值与截断标记。单载荷默认投影上限为 `min(4096, floor(0.10 × H))` 个估算 token；整组再服从组装预算。

增加只读 `context_result_read` 工具，使用不透明引用、字节 offset 和请求字节上限读取脱敏原文。响应包含实际范围、下一页位置、总长度与 SHA-256；必须保证 UTF-8 边界正确。默认每页不超过 4096 字节，同时服从模型投影预算。

该工具仅在 Hierarchical 新策略下作为受控工具可见，绑定当前会话和固定身份，不能接受任意文件路径、URL 或 SQL。读取不能绕过资源归属，不能跨会话获取其他执行的载荷。历史来源已不存在时返回明确状态。

输入参数与输出一样需要有界处理，尤其是大文件修改正文。完整安全内容可以归档，但生成模型输入时可用带引用的历史参数投影；不得将历史投影重新当成待执行工具参数。调用 ID、工具名和工具结果的配对必须保持。

### 8.3 轮询去重

仅对白名单只读状态工具应用确定性投影，例如对同一个 validationId/queryId 的连续轮询。保留最新状态、首次接收、终态、错误与状态转换；不得按相同文本合并写操作，也不得合并不同 workspace/branch/release 的结果。

轮询折叠作为摘要源中的带范围事实，覆盖全部被折叠步骤；原始协议后缀要么保留完整组，要么整组进入摘要，不能单独删除某条 observation。

## 9. 发布、失败与重启

沿用不可变 Cold + checkpoint CAS。覆盖游标、策略版本、摘要 schema 版本、来源摘要和摘要引用同时受发布校验，不能只更新其中一部分。

候选生成期间不持有长数据库事务。生成后先核对执行权、取消和 deadline，再在短事务中验证预期 checkpoint 并发布。CAS 失败只读取胜出的状态，不覆盖，不重放业务工具；取消后不发布摘要。未被 checkpoint 引用的候选不能进入模型输入。

摘要生成失败时保留旧摘要与所有原始步骤。当前投影仍在硬预算内，可以继续当前 execution，但同一历史/工具集合/预算指纹不重复尝试失败的压缩；新的实际步骤或预算变化才允许下一次尝试。

已经超过硬预算时返回明确的上下文压缩失败及原因，沿用现有 execution 失败收敛，不引入新的暂停状态机。压缩失败不产生确认、不重试 push、不清理草稿。用户再次提交时可复用有效历史，但不能承诺从中断指令自动恢复执行。

服务重启后按现有规则将未完成 execution 收敛，保留已发布摘要和业务工作区。后续同会话的新 execution 从 checkpoint 和原始后缀重建；本设计不改变既有单实例执行恢复政策。

## 10. 存储兼容与迁移

迁移采用增量列与增量安全载荷表，字段均写数据库注释。Hierarchical Cold/checkpoint 增加策略/schema 标识、步骤覆盖和观察位置；旧轮次/消息字段留作兼容与审计，不能把旧字段改名为步骤序号继续使用。

V2 摘要及共享 `EventSummaryCoverage` 不改变含义。新 Hierarchical V3 使用独立的步骤范围与来源校验，避免改变 LSM 的 V2 schema、输入选择和恢复行为。

读取旧 Hierarchical checkpoint 时，以其原始消息与真实工具记录，将已覆盖的完整消息结束位置转换成 V3 游标；旧摘要内容与旧来源范围作为已验证基础导入，不覆盖原文档。没有足够来源证明完整范围时不得猜测位置，改由保留的真实历史重建；若材料缺失则报告迁移/恢复失败。

首次成功发布 V3 才推进 active 指针，失败保持旧状态可审计。迁移和首次转换必须可重试。同一部署中的 Hierarchical 执行实例统一升级；旧代码不能读取 V3 后继续写回旧覆盖位置。部署回滚需恢复匹配的数据快照，不把数据库兼容列误认为旧算法能够安全消费 V3。

## 11. 模块职责与范围

| 模块 | 改动职责 |
|---|---|
| `agent-domain` | 步骤游标、原子组、V3 摘要范围和结果引用等纯协议对象 |
| `agent-context-hierarchical` | 历史步骤投影、预算规划、分批摘要、组装与发布协调 |
| `agent-context-common` | 复用已有安全包装与结构校验惯例；V3 支持不得改变 V2 语义 |
| `agent-persistence` | 增量迁移、Cold/checkpoint CAS、安全载荷 Entity 与 MyBatis-Plus Service |
| `agent-web` | 工具终态安全原文归档、明确失败原因、现有 ReAct 检查点衔接 |
| `agent-tool` / `agent-skill` | 受控只读结果读取、当前 execution Skill 来源与激活事实 |
| `agent-server` | 策略预算与工具装配配置、README 对应配置说明 |
| `agent-evals` / 归属模块测试 | 单轮多次压缩、协议配对、恢复与业务副作用的验证 |

不新增产品级模块、外部存储服务或模型供应商依赖。不改 Git push、dbt 校验、指标发布的业务授权协议；压缩只影响送入模型的上下文投影与相关持久化。

## 12. 验收矩阵

| 场景 | 必须证明的结果 |
|---|---|
| 单用户请求、至少 40 个完整 ReAct 步骤 | 在同一 execution 中至少成功发布两次摘要，最终完成回答，无需新会话 |
| 三个用户轮次，每轮包含大工具结果 | 不再被固定十轮规则阻断；当前用户原请求始终存在 |
| 一次模型调用多个工具 | 只有全部终态后整组可压缩；每个 provider 输入中的调用/结果配对合法 |
| 超大单轮、超大单步骤、超大工具参数 | 按步骤与载荷预算处理，摘要模型每批也不超预算；引用可读取，超存储上限如实标记 |
| 同消息多次压缩并继续追加步骤 | 覆盖游标单调，无遗漏或重复注入；消息封口不把后来步骤误归已覆盖 |
| 重复状态轮询 | 同对象状态可折叠；错误、终态、不同对象和写操作不被错误合并 |
| 摘要损坏、伪造范围、越权引用 | 拒绝发布；不改变授权、工作区或执行事实 |
| 取消、deadline、CAS 竞争、进程重启 | 未授权候选不生效；保留原文与旧 checkpoint；不重复执行写操作 |
| V2 旧会话迁移与 LSM/raw 回归 | 新游标可验证映射，旧摘要不被覆盖；LSM/raw 现有语义不变 |
| Git/指标完整流程 | 同一会话同一用户请求内发生多次真实压缩后，仍能生成正确候选并经用户确认推送、发布、查询；共享 main 不合入测试定义 |

端到端模型替身必须实现合法摘要返回并记录摘要调用，而不是只返回业务工具指令。既断言摘要调用确实发生，也断言 checkpoint 发布、覆盖推进、后续上下文使用了摘要及业务最终结果正确。确定性测试不宣称验证了真实模型摘要质量；另用脱敏样本评估关键事实与约束保留。

40 步验收夹具显式配置足够的 ReAct 次数上限和截止时间，不修改生产默认上限；另设负例验证压缩前后累计调用次数不被重置。预算用可控的小窗口加大结果稳定触发，不能依赖机器速度或偶然轮询次数复现。

以现有 README 支持的命令运行最小相关测试，再执行涉及模块的构建验证。旧“十轮原文保护”测试不得直接删除：保留旧版本兼容验证，新版本增加已批准语义的回归；协议配对、取消、CAS 和权限测试不能弱化。

## 13. 可观测性与完成条件

记录压缩前后估算量、必要输入/摘要/原文/工具定义分项预算、触发原因、覆盖区间、压缩次数、摘要失败原因、CAS 冲突及载荷读取结果。沿用现有指标设施；原文和凭据不进入新增诊断日志，详细游标放在可控审计记录中，避免高基数指标标签。

书面规格批准后编写实施计划，逐项落实模块与验证依赖。全部验收完成前不能把“换会话成功”当成本轮压缩通过，也不能把压缩流程被调用但未生成摘要当作成功。
